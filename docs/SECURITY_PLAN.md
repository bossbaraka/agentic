# خطة الأمان — MUREEH Agent

> وثيقة تهديدات وضوابط، مكتوبة قبل التنفيذ ومتحقَّق منها في الكود النهائي.

## 1. سطح الهجوم

| المصدر | التهديد | الضابط |
|---|---|---|
| Webhook واتساب | تزوير أحداث | التحقق HMAC-SHA256 على الجسم الخام قبل الرد (`verifyMetaSignature`) |
| Webhook تيليجرام | تزوير تحديثات | `secret_token` عشوائي (`TELEGRAM_WEBHOOK_SECRET`) يُتحقق منه (`verifyTelegramSecret`) |
| لوحة التحكم | وصول غير مصرّح | كلمة مرور عبر استعلام/كوكي HttpOnly + SameSite=Lax |
| رسائل العميل | Prompt Injection | انظر §3 |
| استدعاء أدوات النموذج | حجز/إلغاء/تسريب بيانات | عقد أدوات + تحقق + ملكية + تدقيق + idempotency (§4) |
| أوامر/أزرار الإدارة | تصعيد صلاحيات | RBAC صريح default-deny (§5) |
| الإدخال العام | حقن/فيض/أحمال | متحققات صارمة وحدود طول في `toolRegistry` وحد حجم الجسم 8MB |
| الرصيد/الحلقات | استنزاف LLM | Rate limiter نافذة منزلقة لكل مفتاح (`RATE_LIMIT_PER_MIN`) |

## 2. الأسرار والإعدادات

- لا أسرار في الكود: كل المفاتيح والتوكنات وكلمات المرور من متغيرات البيئة (راجع
  `.env.example`). لا أسعار ولا معرّفات مدير في منطق الأدوات.
- الأسعار الوحيدة المسموح بها مصدريًا هي `src/agent/plans.ts` التي تُزرع في DB؛
  الكتالوج المعروض يُقرأ من قاعدة البيانات عبر `catalogService`.
- عند غياب `WHATSAPP_APP_SECRET` يسجّل الإقلاع تحذيرًا صريحًا، وفي وضع التجربة
  فقط يُسمح بتجاوز التحقق.
- `/internal/simulate` مغلق في الإنتاج (`INTERNAL_TEST_HOOK` أو DEMO_MODE فقط).

## 3. الحماية من Prompt Injection

مبدأ: **محتوى العميل بيانات، ليس تعليمات.**

1. تعليمات النظام (`src/agent/systemPrompt.ts`) تمنع صراحة إفشاء التعليمات
   ("تجاهل ما سبق"، DAN، "كرّر ما قلت")، وتعتبر أي تعليمات داخل نص رسالة/صورة/
   مستند بيانات للقراءة فقط.
2. قائمة الأدوات ثابتة في الكود (`TOOL_DECLARATIONS`)؛ لا يستطيع النموذج تعريف
   أداة ولا استدعاء اسم غير مسجّل: `executeTool` يرفضه ويدقّق `tool.denied`.
3. النموذج **لا ينفذ** عملية أعمال بنفسه؛ يطلب فقط عبر أداة، والطبقة الموثوقة
   (services) تعيد التحقق: صيغة المدخلات → الملكية → قواعد العمل ضمن معاملة.
4. لا يمكن لرسالة عميل أن تغيّر دور/صلاحية/أدوات الجلسة.
5. عند الجهل أو التصادم أو طلب العميل الصريح: تحويل بشري، والبوت يصمت
   (`handoffService` + حالة `human`).

## 4. عقد استدعاء الأدوات (toolRegistry)

- **تحقق قبل التنفيذ** (`validate` لكل أداة): تواريخ `YYYY-MM-DD`، أوقات `HH:MM`،
  تعدادات، أرقام بنطاقات، حدود طول (ملاحظة ≤300، مشكلة ≤2000…). الفشل يمنع
  التنفيذ ويعيد خطأ منظمًا.
- **التقاط شامل للاستثناءات**: لا يصل استثناء قط لحلقة النموذج؛ النتيجة دائمًا
  `ToolResult { ok, data, userMessage?, sideEffect? }`.
- **تدقيق**: كل أداة `mutating` (إنشاء/تعديل/إلغاء حجز، تذكرة، إشعار، تحويل،
  تأكيد طلب) تكتب صفًا في `audit_logs` مع الفاعل والسياق؛ المرفوض والفاشل
  يُدقّقان أيضًا (`tool.denied`/`tool.failed`).
- **الملكية**: إلغاء/تعديل/عرض حجز أو طلب يمر بـ `requireOwnedBooking` /
  `orderService.byRef(ref, key)` — يُقارن `contact_key` بالجلسة.
- **Idempotency**: مفاتيح ثبات على الحجوزات والطلبات تمنع ازدواج الناتج عن
  إعادة المحاولة أو ضغطة زر مزدوجة (UI أيضًا تضع مفتاحًا قاعديًا ثابتًا لكل
  جلسة/فتحة).
- **ثبات الأدوات للقراءة** فقط ممكن للنماذج؛ العمليات المالية والموظفون خارج
  متناولها تمامًا.

## 5. RBAC (src/services/rbac.ts + adminService)

- أدوار: `SUPER_ADMIN > ADMIN > MANAGER > STAFF`، مصفوفة صلاحيات صريحة
  (default deny: أي صلاحية غير مذكورة ممنوعة).
- `adminService.guard(admin, permission)` نقطة مرور إجبارية لكل عملية إدارية:
  قراءة/كتابة الحجوزات والطلبات والتذاكر، تفعيل الخدمات، إدارة الموظفين،
  التدقيق، المقاييس، استلام المحادثات.
- ربط الموظف بمعرّف تيليجرام الرقمي؛ غير الموجود في جدول `admins` النشط يحصل على
  تنبيه رفض ولا تُنفّذ أي عملية.
- المشرفون الأعلى يُزرعون من `ADMIN_TELEGRAM_IDS` (لا حسابات مخفية في الكود).
- مغطى باختبارات: رفض غير الموظف، رفض STAFF للكتابة، رفض MANAGER لإدارة الموظفين،
  السماح المحدود لكل دور.

## 6. التحويل البشري وصمت البوت

- التحويل يحدث بثلاث طرق موحّدة عبر `handoffService`: زر العميل، أداة
  `handoff_to_human`/تذكرة، قرار النموذج (`handoff=true`).
- الحالة تُكتب في مخزن الجلسة **و** جدول conversations؛ في حالة `human`/`paused`
  يصمت المنسّق تمامًا عن الرسائل الجديدة، ولا يعود البوت إلا بقرار موظف
  (`/resumeadmin` أو لوحة التحكم أو adminService.resume).
- ردود الموظفين اليدوية تُسجّل وتُدقّق كأي رسالة صادرة.

## 7. الموثوقية والخصوصية

- طابور إشعارات دائم في DB مع حالات PENDING/PROCESSING/SENT/FAILED/CANCELLED،
  تراجع أُسي و`NOTIFICATIONS_MAX_ATTEMPTS`، وعامل أحادي التشغيل (re-entrancy guard).
- نقاط الفحص: `/health` (قاعدة البيانات، القنوات، عمق الطابور) + Docker healthcheck.
- أرقام العملاء تُطبع مقنّعة في السجلات (أول 3 وآخر 4) في مسارات التنبيه.
- بيانات الاعتماد لا تُسجّل، وكلمات المرور تُمرر عبر متغيرات البيئة فقط.

## 8. قيود معروفة (بشفافية)

- Rate limit في الذاكرة لكل عملية (خلف عبار حمل متعدد يحتاج مخزنًا مشتركًا أو
  تقييدًا على مستوى الشبكة) — مناسب لبوت قناة واحدة؛ يُوسّع لاحقًا بـ Redis.
- كلمة مرور لوحة واحدة (تكفي لفريق صغير)؛ لمتعدد الموظفين عبر الويب يلزم جلسات
  دخول كاملة.
- لا تكامل دفع مالي بعد (`payments` مجهّز المخطط؛ التنفيذ خارج النطاق الحالي).
